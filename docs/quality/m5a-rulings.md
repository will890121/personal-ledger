# M5a 執行期間的裁決紀錄

M5a（Google Sheets 鏡像）以 subagent-driven development 執行：13 個任務，每個任務派一個
實作者與一個審查員，修正回合再派複審，最後一輪整分支審查。執行期間不停下來問人，
遇到衝突、歧義、計畫缺陷就當場裁決並記錄。

這份文件是那些裁決的彙整。來源是執行帳本（`.superpowers/` 為拋棄式暫存，分支收尾即刪除）。
共 69 條裁決。按性質分組，不按時間排列。

---

## 一、這個里程碑的主題：程式是對的，而沒有任何東西讓它保持正確

M4 的主題是「程式對、測試空轉」。M5a 的主題更精確一點：**今天為真，而沒有任何機制讓它
明天還為真。** 幾乎每一個真實缺口都是這個形狀，每一次都是審查員用變異證明的。

| 被改壞的東西 | 當時的結果 |
|---|---|
| 正式的 client 不包 `withHeaderRows` | 644 條全綠 —— 正式環境可以完全不寫標題列 |
| 游標比較的**外層** `>` 改成 `>=` | 7 條全綠 —— 邊界列每一 tick 被重送，永不停止 |
| `buildWrites` 裡「不准動手打列」的守衛刪掉 | 479 條全綠 —— 使用者的註記列會被清空 |
| 校正被截斷時的兩個守衛各自刪掉 | 564 條全綠 —— 實測清空 100 列真實資料 |
| `allocationRows` 的 D–J 七欄換成常數 | 564 條全綠 —— Allocations 分頁內容零斷言 |
| `close()` 的 `sheetRunner?.stop()` 刪掉 | 644 條全綠 —— SIGTERM 後行程永不退出 |
| 告警的 `chatId` 寫死成錯誤值 | 644 條全綠 —— 告警永遠不會到 |
| OAuth scope 擴大成整個 Drive | 全綠 —— 金鑰洩漏的影響範圍從一張表變成整個 Drive |
| 同時違反三條分層邊界 | `pnpm check` exit 0 —— 架構約束只是註解 |

**裁決：每一條都退回補測試或補把關，沒有一條以「反正實作是對的」放行。**

最後一項尤其重要，因為它是前面幾項的根因：三條分層規則被寫進文件、寫進註解、被程式碼
依賴，而完全沒有東西強制。現在由 `eslint.config.mjs` 的 `no-restricted-imports` zone 把關。

### 那條規則真正擋得住什麼（刻意記錄它的射程）

擋得住：type-only import、子路徑 import、re-export。
**擋不住**：動態 `import()`、傳遞路徑（A import B，而 B import googleapis）。

`no-restricted-imports` 比對的是「這個檔案的 import 行」，不是依賴圖。要擋傳遞路徑得引入
dependency-cruiser，代價超過它在這個專案消除的風險。**這個射程寫在設定的註解裡** ——
一條宣稱自己擋得比實際多的規則，比沒有規則更危險。

## 二、推翻我自己的裁決

### 1. 游標比較：`>=` 改成嚴格 `>`

我原本定 `>=`，理由是「兩列可能共用同一毫秒，用 `>` 會漏掉」。**那個理由是錯的。**
游標存的是 tuple `(updated_at, transaction_id)` 而 `transaction_id` 唯一，所以 tuple 上的
嚴格 `>` 就是全序上的「嚴格在游標之後」，同毫秒但排在後面的列靠 `transaction_id > c2`
照樣收得到。我的理由只在游標是單一純量時成立。

代價是實測出來的：seed 兩筆交易後靜置五個 tick，得到 `synced(2), synced(1), synced(1),
synced(1), synced(1)` —— 邊界那列每一 tick 都被重送，每分鐘 12 次 API 呼叫，永遠不停。
而 §7 的配額設計整個建立在「閒置 0 次」上。使用者看到的是一張永遠顯示「幾秒前編輯」的表。

### 2. 孤兒列清理：從「A 欄非空」收窄成「A 欄是 UUID 形狀」

我要求「清掉 SQLite 裡不存在的列」。實作者照做，然後回報實際效果：**任何 A 欄非空的列，
每天被默默清空一次。** 你貼幾列上去對照、或在空白列寫個備註，隔天就消失。

我要解的問題從來不是「使用者加了東西」，而是「鏡像自己留下的孤兒與重複列」——
我的規則把兩者混為一談。收窄成 UUID 形狀（id 都來自 `randomUUID()`，所以這個條件精確
等於「這列只可能是鏡像自己寫的」），並要求一條反面測試：手打的列跑完校正必須還在。

### 3. 「兩條部署路徑都要能用」—— 我沒查證就寫進 brief

`compose.yaml` 用明列式 `environment:`，兩個新變數不會被轉發；而且它宣告的
`personal-ledger_ledger-data` **根本不存在**。所以 `docker compose up -d` 會建一個全新的
空資料庫 —— 照文件走的人會把新帳記進空庫，而真帳本在另一個卷裡，資料分裂且無任何錯誤。

修法：把卷名釘死（`name: m1-foundation-first-slice_ledger-data`），不用 `external: true`
（那會壞掉全新檢出）。

## 三、會造成實際損害而被擋下的

### 1. 驗收文件裡有一條會清空你試算表的路徑

保護正式試算表的守衛需要 `SHEET_SPREADSHEET_ID` 在同一個環境裡，但文件的指令範例只設
兩個測試變數，而專案沒有任何東西載入 `.env`。實測：測試變數填正式 id 而正式變數未設 →
**「拒絕執行」出現 0 次**，直接進 `clearWorkbook()`。

而文件第 3 步就要求把正式 id 填進 `.env`，所以四段之後複製過去是最自然的動作。
三張真實分頁上每一列有內容的列，在任何斷言之前被清空，無法還原。

兩層都修了：文件的指令前載入 `.env`；測試動手前印出即將清空的試算表 id，
並在無法比對時明說「我無法確認這不是你的正式試算表」。

### 2. 校正被截斷後每 20 秒重跑，並讓增量同步整天停擺

兩道截斷守衛在**正確性**上合得起來，在**活性**上合不起來：`lastReconciledAt` 只在完整
掃完時才蓋，而排程判斷「今天校正過了嗎」讀的就是它。實測十次 tick 全是校正、零次增量。

門檻是兩萬筆交易（對這本帳本是好幾年後），但形狀是「兩道守衛被以為合得起來、實際上沒有」。
修法：把**排程判斷**與 **`/status` 顯示的事實**分開，`lastReconciledAt` 語意一字未動。

### 3. `close()` 不停 runner → `docker stop` 只能 SIGKILL

SIGTERM 之後資料庫關了，但 20 秒的 interval 還活著 —— tick 打在已關閉的連線上，
而活著的 interval 讓事件迴圈不結束。

## 四、關於「不要採信，去量」

這條紀律在這個里程碑出現四次，**其中三次是我違反的**：

1. 我照抄實作者回報的「`.run()` 傳 12 個值對 11 個佔位符」寫進計畫。審查員數過是 11 對 11。
2. 我照抄「這個修法順帶也解決了 N-1」。複審實測：661 條全綠，沒有解決。
   **附帶宣稱最不可信** —— 它不是那次工作的主題，實作者不會特地去驗，
   而它聽起來像額外的好消息。
3. 我自己推論「手動刪掉舊月份摘要列之後不會自動補回」並寫進帳本。整分支審查實測：
   **會補回來**。`affectedMonths` 對每一筆交易無條件加入其月份，而 reconcile 掃全表。
4. 最後一次方向相反：我跑完整檢查得到 exit 1、與實作者回報不符，差點記成「宣稱有誤」。
   查下去是主機負載 99.85 造成的逾時。等負載降到 14.8 重跑 → exit 0。
   **宣稱是真的，誤導的是我的量測。**

紀律兩邊都要適用，否則它只是另一種偏見。

## 五、接受實作者推翻我的

- **拒絕做頁間節流**（Task 9）。理由比我的假設好：reconcile 對 runner 不透明、實際帳本
  7 筆交易、過大的校正已由頁數上限安全降級。我補上一個它沒說的理由：**超出配額的後果
  本身是良性的**（429 → transient → 游標不動 → 重試）。
- **`laterCursor()`**（Task 6）。我說 reconcile 就是 `cursor = null`；照字面做會讓游標倒退，
  每天的校正等於把整個同步重啟一次。
- **I-1 的標記放行程內狀態**（最終修正）。持久化會多一個必須與 `lastReconciledAt` 對齊的
  時間戳，而「兩個狀態各自寫、各自可能不同步」正是 I-1 本身的形狀。
- **N-1 的修法**：它先查了我建議的做法行不行 —— 那條測試早就存在，但 GoogleAuth 惰性
  建構讓它抓不到欄位互換。改用 passthrough spy。**先驗證指示可不可行再執行。**

## 六、計畫本身的缺陷（全部當場更正並提交）

- Task 2 的測試 seed 與真實 schema 有四處不符 —— **那段 seed 我是照著 migration 檔案寫的，
  從來沒有執行過。** 寫進計畫的程式碼沒跑過就只是假設，而計畫的權威性會讓實作者當成事實。
- Task 4 的測試檔完全沒有測 `monthlySummaryRow` —— 相鄰兩欄對調不會有任何紅燈。
- Task 6 的測試只有註解沒有程式碼（那是計畫失敗，不是風格問題）。
- Task 7 的文字在我採納 `laterCursor` 之後自相矛盾。
- spec §9 要求的「替身 vs 真實」差分測試沒有落在任何 task。
- Task 8 的升級通知沒有任何 task 真的接到 Telegram。
- **brief 是快照**：我在產生 brief 之後才改計畫，磁碟上那份完全沒有新需求。
  實測舊 brief 提到 compose 0 次、計畫 4 處。往後一律在派工前當場重新產生。

## 七、流程

- **實作者一次只能有一個**，即使檔案不重疊 —— 兩個同時在同一工作區跑 `git add`／`commit`
  會互相把對方半成品的變更 stage 進去。審查員（唯讀、在拋棄式 worktree）可以並行，
  上限兩個：每個都在 Docker 裡跑 `pnpm check`，主機忙碌時 `tests/startup.test.ts` 的
  build hook 會逾時，產生與改動無關的假紅燈。（這個里程碑最後負載衝到 99.85，代價結算了。）
- **收緊測試替身要排在使用它的 task 之後**，否則實作者會在不知情的情況下踩到新規則，
  而那個錯誤看起來像是它自己寫壞的。
- **Minor 原則上不進修正迴圈**，但已經因為 Important 必然要開一輪、改的是同一個檔案、
  且只有五行時，折進來不會延長迴圈 —— 有意識地偏離並記錄。
- **一條測試的修正我自己變異驗證**，不派完整審查座位（M4 已有先例）。
- **缺少的報告由我轉錄，但標明不是實作者寫的** —— 稽核軌跡的價值在於完整，
  但假造作者身分會讓它變成反效果。
