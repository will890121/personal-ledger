# M4 執行期間的裁決紀錄

M4 以 subagent-driven development 執行：15 個任務，每個任務派一個實作者、一個審查員，
修正回合再派複審。執行期間不停下來問人，遇到衝突、歧義、計畫缺陷就當場裁決並記錄。
這份文件是那些裁決的彙整，來源是執行帳本（`.superpowers/` 為拋棄式暫存，分支收尾即刪除，
因此在這裡留一份）。

共 39 條裁決。按性質分組，不按時間排列。每條都附「若判斷錯誤的代價」——那是當初決定
要不要停下來問人的依據。

---

## 一、貫穿整個里程碑的那一件事：程式對，但守衛是空的

**15 個任務裡有 13 個出現同一種形狀：實作是對的，測試沒有守住它。**
每一次都是審查員用變異測試證明的——把實作改壞，測試照樣全綠。

實際發生過的變異，每一個都曾經全綠通過：

| 被刪掉／改壞的東西 | 當時的測試結果 |
|---|---|
| `synchronous = FULL` | 全綠（SQLite 本來就預設 2，狀態式斷言分不出「我們設了」與「預設就是」） |
| `VACUUM INTO` 換成 `copyFileSync` | 四條快照測試全綠，而 WAL 正是選 `VACUUM INTO` 的全部理由 |
| 六個日誌遮罩欄位刪掉五個 | 全綠（只有 `rawText` 被釘住，`text` ——grammY 放訊息內容的欄位名——完全沒守） |
| 退款確認的 `replyMarkup` 整個拿掉 | 438 條全綠 |
| 同一則訊息送兩次 | 438 條全綠（既有測試只看 `calls.at(-1)`，被最後的清單重繪遮住） |
| `/status` 的 `attempts` 改成 `attempts + 1` | 446 條全綠 |
| 警示文案後面接上金額 | 全綠 |
| 「強制改送新訊息後那次也失敗」改成靜默吞掉 | 11 條全綠 |
| `MAX_REDACTION_DEPTH` 從 8 改成 100000（等於關掉深度上限） | 18 條全綠 |

**裁決：每一條都退回補測試，沒有一條以「反正實作是對的」放行。**

理由：一個空轉的守衛比沒有守衛更糟。沒有守衛時，下一個人知道自己在沒有保護的情況下改；
有一個假守衛時，他以為紅燈會救他。這個專案的價值在於帳目正確，而帳目正確靠的是
「改壞了會有人告訴我」。

代價：多了約 40 條測試與對應的維護成本。

### 衍生的一條方法論裁決

**變異驗證是驗收標準，不是加分項。** 往後每一次 dispatch 都明寫：宣稱某個行為被保護，
就要附上「把它改壞、測試變紅」的證據與失敗訊息原文。審查員自己也要重跑一遍，不採信
實作者的自我回報——本里程碑至少兩次，實作者回報的「已驗證」是假的（見下方 Task 13）。

## 二、產品語意的裁決

這些是「兩種做法都能讓測試變綠，但只有一種是對的」的情況。

### 1. `/status` 的「卡了多久」讀 `created_at`，不讀 `next_attempt_at`

實作者發現測試不可能通過（seed 沒設 `created_at`，值落到 SQLite 的 `CURRENT_TIMESTAMP`
非 ISO 格式），於是把查詢改讀 `next_attempt_at`，測試就綠了。

**不採納。欄位是對的，測試是錯的。** 「卡了多久」＝ `created_at`；`next_attempt_at` 是
「下次何時該送」，退避中的列那個時間在未來，拿它算會得出**負的年齡**。把測試改綠卻讓
功能變錯，是這個里程碑裡最容易發生也最難發現的一種錯。

改法：還原查詢、seed 明寫 `created_at`、加一條「已失敗過一次、`next_attempt_at` 在未來」
的測試把這個區別釘死。後來在測試替身裡發現同一個潛伏 bug，一併修掉。

### 2. 重試次數顯示 `attempts`，不加一

`markOutboxNeedsAttention` 不動 `attempts`，只有 `markOutboxFailed` 會；上限路徑走前者，
所以停在 4 而不是 5。**這個值是正確的**：第一次送出不是重試，之後排了 4 次重試，總共送 5 次。

裁決：儲存語意不變，`/status` 直接印 `attempts`（「已重試 4 次」字面為真），立刻放棄的列
`attempts=0` 讀起來也正確。替代方案是印 `attempts + 1`，但那個魔術加一更難解釋。

若判斷錯誤的代價：若使用者把「已重試 4 次」讀成「總共只送了 4 次」，會低估一次。

### 3. `/status` 必須用本地時區，這是必修不是追蹤項

`/status` 的用途就是讓人判斷遞送有沒有卡住。差八小時的時間戳會讓使用者以為卡住了——
**那不是不方便，是功能失效。** `main.ts` 既有的 `dateInTimezone` 已經以 `today: () => string`
接進 dependencies，時刻走同一條路徑即可。

### 4. 超收回收的 `cause` 維持 `recovery_recorded`

`cause` 記的是「哪一個使用者動作造成這則訊息」，不是會計分類。使用者按的是回收草稿的
確認鍵，即使那筆同時記了一筆收入。

若判斷錯誤的代價：`/status` 上看不出那筆同時記了一筆收入。

### 5. 通知節流時間只在送出成功時寫入

節流的目的是不要洗版使用者。失敗的通知沒到達使用者，洗不了版；反之若失敗也消耗那 10 分鐘，
Telegram 兩分鐘後恢復時使用者還要再等八分鐘才被告知——那更糟。

代價：斷線期間每一列放棄都會試一次通知（廉價的失敗 API 呼叫）。

### 6. 快照檔名改成「時間戳在前」，而不是修比較子

`pruneSnapshots` 用檔名字典序排序，版本 9 與 10 並存時會排錯。審查員獨立重現後發現比
預估更糟：修剪把排序後的第一個當「最舊」刪除，所以會**刪掉最新那一份**、留下三份陳舊的。

裁決：不修比較子，改檔名格式讓字典序天然等於時間序，從根上消除這一類錯誤。
目前 schema 是 8，這個 bug 會在版本到 10 時才發作，但 M5／M6 就會加 migration。

### 7. 日誌遮罩必須遞迴

原本只處理頂層。「單一出口負責遮罩」的全部意義就是呼叫端不必自己先攤平；只做頂層等於
把保證外包給每一個未來的呼叫端，而 grammY 的 Update 天生深巢狀。

要求遞迴並加上深度上限與循環偵測。後續又發現深度上限本身沒有測試（改成 100000 全綠），
再退一輪補上，並且**兩個方向都要釘**：常數調大調小都必須有紅燈，否則有人把上限設成 1
就能讓遞迴悄悄停擺。

### 8. 合併 `not_found` 與 `nothing_to_abandon` 的訊息，保留

真正的 `not_found` 經由 UI 不可達（`resolveRef` 只會給出曾經存在的 allocation id），
為此還原一個使用者碰不到的分支不划算。要求補註解與測試說明這是刻意的。

若判斷錯誤的代價：若日後有其他入口可觸發 `not_found`，訊息會誤導。

### 9. `/help` 必須涵蓋 spec §6b 的四種語法

第一版只列了四行平鋪範例，漏掉日期前綴、人數平分、回收款、一句多筆。
先自行確認這四種都真的支援（`rule-parser.ts:65`、`split-share.ts:34`、`split-share.ts:86`、
`create-batch.ts` 的 `splitInput`），確認不是 spec 一廂情願，才裁定必改。

`/help` 存在的全部理由就是可發現性，漏掉使用者最會忘的那一半，等於這個功能沒做到它
自己的目的。

## 三、計畫本身的缺陷

計畫是論證文件，不是聖經。實作者與審查員找出的計畫錯誤，一律當場改計畫並提交。

1. `expect(() => fn()).toThrow()` 的單行 arrow 觸發本專案的 `no-confusing-void-expression`。
2. 六個檔案用 `{ version: 7 }` 樣式，實際有一個是扁平陣列 `[1..7]`。
3. `confirmDraft` 是**同步**拋出（better-sqlite3 的 `.immediate()` 直接 rethrow），
   brief 寫的 `rejects.toThrow` 不可能成立。
4. **計畫漏了 `transactions.ts` 的退款確認路徑**（第二個 `confirmDraft` 呼叫）。
   讓 outbox 必填後它會寫入一列，卻仍自己 `editMessageText`——runner 上線後同一則訊息
   會送兩次。併入 Task 8 範圍。
5. 測試 seed 沒設 `created_at`；上限測試斷言 `attempts === 5` 而實際停在 4；
   429 無 `retry_after` 的分支沒有測試案例；logger 測試的假 token 比正規表示式要求的短。
6. `refund-confirm:` handler 沒有被任何 task 認領。

## 四、流程與工具的裁決

### 1. 用分支，不用 worktree
本 session 的環境設定明確要求就地工作，而 skill 的實質要求是「不要直接在 main 上做」。
建分支同時滿足兩者。

### 2. 實作者一次只能有一個
即使檔案不重疊也一樣。兩個實作者同時在同一個工作區跑 `git add`／`commit`，會互相把
對方半成品的變更 stage 進去。Task 11/12/13 都動 `main.ts` 或 `create-bot.ts`，這條不是
保守而是必要。審查員（唯讀）可以並行。

### 3. 實作者模型下限是 sonnet，不是 haiku
Task 1 是「計畫已附完整程式碼」的轉錄工作，haiku 用了 38 個 tool call、29 分鐘。
本專案每一道指令都要經過 Docker，turn 數的代價遠高於 token 單價。改用 sonnet 後同類
任務 3 分鐘。

### 4. 先提交，再做變異驗證
Task 9 的修正實作者在變異驗證中途被 watchdog 中止，**工作區留著被改壞的原始碼**，
而好的工作沒有提交。下一個 agent 可能把壞掉的狀態當成正常。

往後所有 fix dispatch 一律要求：先提交測試，再做變異驗證，一次只改一個地方，
每次變異後立刻還原並以 `git status --short` 確認乾淨。這樣行程中止最多留下一個乾淨的
commit 加一個髒工作區，不會兩頭皆失。

### 5. controller 的檔案改動一律當場提交
Task 1 的審查員用 `git checkout --` 還原了我對計畫的 lint 修正。未提交的工作區改動不安全。

### 6. 派工時當場做的裁決一律進帳本
Task 13 的審查員查不到實作者引用的「Ambiguity #1」——那是我在派工對話裡當場裁決的，
沒有落進任何檔案。決定本身正確，但審查員無從查證。這是對我自己的裁決。

### 7. 「不得修改正式 checkout」這句話要寫精確
寫得太寬，導致審查員不敢把報告寫進 `.superpowers/`（那是 gitignore 的暫存區，正是報告
該去的地方），報告隨拋棄式 worktree 一起消失。改成「不得修改被追蹤的檔案；報告寫進
`.superpowers/sdd/<plan>/`」。

### 8. 小修正自己動手，不派實作者
兩次這樣做：Task 12 的深度上限驗證（改一個常數看紅不紅），以及 Task 14＋15 審查後的
五行清理。派一個新 context 要十分鐘以上，不成比例。前提是有測試可以驗——這也是為什麼
同樣的判斷在有 Task 15 之前是「不要動備份腳本」，之後變成「可以動」。

### 9. 缺少的報告由我轉錄，但標明不是實作者寫的
`task-14-report.md` 不存在，打斷了稽核軌跡。依實作者回傳訊息轉錄補上，檔頭明白標示。
稽核軌跡的價值在於完整，但假造作者身分會讓它變成反效果。

## 五、追加的範圍：Task 15

計畫只有 14 個任務。第 15 個是執行中決定加的。

Task 14 發現 **`scripts/backup.sh` 從 Task 1 切到 WAL 之後就完全壞掉**——來源卷掛 `:ro`，
而 WAL 下 SQLite 連唯讀連線都必須建立 `-shm`，所以腳本直接
`unable to open database file`。那是文件推薦的主要備份路徑，壞了整個里程碑，
**唯一被發現的原因是 Task 14 剛好去跑了一次。**

裁決：把那次手動演練變成 `scripts/backup-selftest.sh`，端到端、自備資料、自行清理。

刻意**不做**的替代方案：在 vitest 裡斷言腳本文字不含 `:ro`。那種斷言只釘住一個歷史拼法、
不驗證備份真的能用，正是這條分支一路在退回的空轉守衛。寧可要一支要手動跑但真的
端到端的腳本。它不能進 `pnpm check`，因為那跑在沒有 docker socket 的容器裡。

### 附帶發現：為什麼那個 bug 躲得過一整個里程碑

`:ro` 並不是每次都會壞。如果 `-shm` 已經存在而且有效，唯讀掛載的讀取端可以正常附著上去。
真正會壞的條件是 SQLite 必須**重建** WAL 索引：`-wal` 裡有已提交但未 checkpoint 的資料，
而 `-shm` 不存在或已失效。

那個條件與「備份最重要的時刻」完全重合：服務非正常結束、`-wal` 裡還有沒落地的交易、
要在 migration 或搶救前拍一份。乾淨關機時 SQLite 會 checkpoint 並移除側檔，那時 `:ro`
反而能過，但那時也沒有 WAL 資料會遺失。

**這個 bug 在所有安全的情況下都隱形，只在真正危險的那一種情況下致命。**
已寫進 `docs/operations/backup-and-restore.md`。
