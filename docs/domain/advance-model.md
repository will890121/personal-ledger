# M3b 代墊與回收設計

- 日期：2026-09-24
- 狀態：待核准
- 里程碑：M3b－代墊與回收

## 1. 目的

M3b 讓使用者記錄替他人墊付的金額、追蹤未回收餘額、登記回收，並在決定不再收回時把代墊轉為個人消費。本設計涵蓋路線圖驗收案例 AC-11 至 AC-14 與 `/advances`。

M3a 已交付批次、追問與待處理清單。M3b 建立在其上：追問用既有的 `pendingFields` 與候選按鈕機制，回收候選清單重用 `/pending` 的分頁模式。

## 2. 範圍

M3b 包含：

- `advance` 與 `advance_recovery` 帳務形狀及其不變條件；
- 分帳語句解析（整除的平分與明確金額）；
- 交易對象的追問與當場建立；
- 回收登記，含部分回收、一次回收多筆與超額回收；
- 放棄回收，含部分放棄與全額放棄；
- `/advances` 未回收清單與餘額。

M3b 不包含：借貸（`loan_out`、`loan_in`、`loan_repayment`）、外幣、月摘要通知、Google Sheets 同步、AI 解析。既有的 `/today`、`/month` 統計不修改——理由見第 8 節。

## 3. 決策摘要

| 決策 | 選擇 | 理由 |
|---|---|---|
| 回收關聯模型 | 回收配置以 `recovers_allocation_id` 指向代墊配置 | 「還了多少」與「還的是哪一筆」是同一個事實，不拆成兩份需要對帳的資料 |
| 未知交易對象 | 追問並以按鈕當場確認建立 | 不猜測，也不必中斷記帳去跑管理指令 |
| 分帳語法 | 可整除的平分（不限人數）與明確金額；除不盡一律追問 | 完全避開四捨五入，金額精度不打折 |
| 多人平分 | 每位參與者各一筆代墊配置，名字不足就追問 | 回收餘額天生按人計算，一人還款不影響他人欠款 |
| 部分放棄回收 | 把原代墊配置拆成「已回收的代墊」與「放棄的支出」兩筆 | 配置合計仍等於交易總額，統計不重複計算 |

## 4. 資料模型與不變條件

### 4.1 Migration 0005

`allocations` 新增可空欄位 `recovers_allocation_id TEXT REFERENCES allocations(allocation_id)`，並建立索引 `allocations_recovers_idx ON allocations(recovers_allocation_id)`。

這是單純的 `ALTER TABLE ADD COLUMN`，不需要重建資料表，也不需要 migration 0003 那套外鍵開關處理。

### 4.2 新增的帳務形狀

`supportedAccountingShapes` 新增三種：

| 形狀 | 情境 | 統計意義 |
|---|---|---|
| `outflow:advance` | 以現金或銀行付款的代墊 | 計入實際流出，不計入個人消費 |
| `none:advance` | 以信用卡付款的代墊 | 兩者皆不計，但仍是應收 |
| `inflow:advance_recovery` | 收到還款 | 計入實際流入，不計入個人收入 |

`none:advance` 涵蓋刷卡分帳。少了它，`聚餐 1260 國泰卡，三個人平分` 會在領域層被整張擋下，而錯誤訊息只會說形狀不支援，使用者無從理解。

### 4.3 不變條件

領域層在持久化之前驗證：

1. `recovers_allocation_id` 只能出現在 `purpose=advance_recovery` 的配置上。
2. 被指向的配置必須屬於同一擁有者、位於未刪除的已確認交易，且 `purpose=advance`。
3. 指向同一筆代墊的回收金額合計不得超過該代墊配置金額。超出的部分必須自成一筆配置並另外分類。
4. 回收配置沿用被回收代墊的分類與交易對象，不另外詢問。
5. `purpose=advance` 的配置必須有 `counterparty_id`。

### 4.4 未回收餘額

餘額是推導值，不落地為欄位：

```text
未回收餘額 = 代墊配置金額 − 指向它的回收配置金額合計
```

放棄回收會縮小代墊配置本身（見第 7 節），因此放棄的部分不需要在公式中另外扣除。沒有需要維護的狀態，也就沒有對不上的可能。

### 4.5 軟刪除與關聯

代墊交易一旦有回收配置指向它，就不得軟刪除：刪除後餘額公式會少掉被減數，而回收配置仍指向一筆已排除於統計之外的代墊。M3b 在刪除流程中擋下這種情形，並告知有幾筆回收指向該交易，請使用者先處理回收。

回收交易本身可以軟刪除。刪除後其配置排除於統計與餘額計算之外，對應代墊的未回收餘額自動回升——這是正確的結果，不需要額外補償動作。

餘額計算一律只納入 `status=confirmed` 的交易，與既有統計規則一致。

規格第 7.6 節描述的「顯示影響清單，讓使用者選擇解除關聯或一併軟刪除」需要更完整的維護流程，留待後續里程碑；M3b 先以明確拒絕保證資料不會出現懸空關聯。

## 5. 代墊建立與分帳解析

### 5.1 語法

解析器支援兩種寫法，皆為確定性規則：

- **平分**：`一半`、`各半`、`平分`、`N 個人平分`。參與人數 `N` 包含使用者本人；`一半` 等同 `N=2`。每人負擔 `總額 ÷ N`，使用者自己留一份，其餘 `N−1` 份各自成為一筆代墊配置。
- **明確金額**：`小明欠 630`、`幫小明付 630`。代墊金額直接取用，不做除法。

### 5.2 除不盡即追問

`總額 ÷ N` 除不盡時不建立草稿的代墊部分，改追問代墊金額。這條規則讓系統永遠不需要決定「誰吃掉小數」，與規格「金額不明必須追問」一致。

### 5.3 交易對象

代墊配置必須有交易對象。解析出的名字逐一比對 `counterparties`：

- 名字存在：直接使用。
- 名字不存在：追問「尚未建立『小明』這個交易對象，要建立嗎？」，附「建立並繼續」與「取消」兩顆按鈕。按下即建立並補完草稿。待建立的名字存放在 `pendingFields` 的 `proposedName`，不放進 callback，避免中文名稱撞上 64 bytes 上限。
- 名字數量少於 `N−1`：追問缺少的交易對象。

### 5.4 追問欄位擴充

`ParseField` 新增兩個值：

- `counterparty`：缺交易對象，或對象尚未建立。
- `advanceShare`：除不盡或語句未表明代墊金額。

`PendingField` 新增可選的 `proposedName`，供「建立新對象」的確認流程使用。既有的候選按鈕與金額回覆機制不變；`counterparty` 的追問同時提供既有對象的按鈕與「回覆本訊息輸入新名稱」的路徑。

## 6. 回收流程

### 6.1 入口

兩條路徑，都收斂到同一個應用服務：

- 文字：`小明還 300`、`收到小明 300`。
- 按鈕：`/advances` 清單中該對象的「記錄收款」。

### 6.2 候選與分配

系統以**先進先出**分配：最早的代墊先沖抵，逐筆填滿到金額用盡。預覽逐筆列出沖抵明細（日期、原金額、本次沖抵），確認後才入帳；分配結果不符預期時，使用者取消即可。

M3b 不提供「逐筆指定要沖抵哪一筆」。先進先出是可預測的規則，而預覽加取消已足以避免錯誤入帳；逐筆指定的介面留待 M6 dogfood 觀察實際需求後再決定。

回收交易若在語句或候選選擇中指明收款帳戶，就記入 `accountToId`；未指明則留空，與既有收入交易的處理一致。

回收交易的每一筆配置對應一筆代墊：

```text
甲的未回收：A1 = 100（3/1）、A2 = 200（3/5）
甲一次還 300
→ 回收交易總額 300，兩筆配置
   R1 = 100 → A1
   R2 = 200 → A2
```

### 6.3 超額回收

收到的金額超過該對象未回收總額時，超出的部分自成一筆配置，`fundsEffect=inflow`、`purpose=income`，並追問分類。這是 AC-14：代墊 630、收到 700，其中 630 沖抵代墊，70 另行分類。

超額部分不得沖抵其他對象的代墊，也不得自動視為收入分類。

## 7. 放棄回收

### 7.1 觸發

`/advances` 清單中每筆代墊提供「放棄回收」按鈕，按下後顯示影響金額並要求再次確認。

### 7.2 兩種情形

- **部分放棄**（已有回收）：原代墊配置金額改為已回收合計，另新增一筆 `purpose=expense` 的配置，金額為放棄額，沿用原分類與交易對象。交易總額不變，配置合計仍等於總額。
- **全額放棄**（尚無回收）：直接把該配置的 `purpose` 由 `advance` 改為 `expense`，不拆分。若拆分，原代墊配置金額會變成 0，違反「配置金額必須為正數」。

### 7.3 稽核與統計

放棄回收是對已確認交易的修改，沿用既有的 `updateTransaction`，在同一個 SQLite transaction 寫入 `transaction_updated` 稽核事件與前後快照，來源事件為該次 callback。

放棄的消費歸屬**原交易日期**，因此原月份的個人消費會追溯增加。這是規格與 AC-13 明定的行為：決策日期記在稽核事件，消費歸屬記在交易日期。

M3b 不新增稽核動作類型：回收是新交易（`transaction_created`），放棄是修改（`transaction_updated`），關聯本身是配置欄位而非 `transaction_links`，不需要 `transaction_linked`。

## 8. `/advances` 與統計

`/advances` 依交易對象分組，顯示每人未回收總額與筆數；展開後逐筆顯示日期、原金額、已回收與餘額。每筆提供「記錄收款」與「放棄回收」。分頁沿用 `/pending` 的模式，每頁 10 筆，並提供「關閉清單」。

**既有統計程式不需要修改。** `summarizeAllocations` 依 `purpose` 分派：`advance` 的 `fundsEffect=outflow` 使其計入實際流出，而 purpose 不屬於 `expense` 或 `fee`，因此不計入個人消費；`advance_recovery` 同理只進實際流入，不進個人收入；分類排名只納入 `expense`、`fee`、`refund`，代墊不會污染分類統計。這正是規格第 9 節要求的雙口徑語意。

未回收代墊總額只出現在 `/advances`。月摘要的未回收代墊欄位屬於第二階段，不在 M3b 範圍。

## 9. 模組邊界

新增：

- `src/domain/advance.ts`：餘額計算、先進先出分配、放棄回收的配置拆分。純函式，不依賴儲存層。
- `src/parser/split-share.ts`：分帳語句解析，輸入文字與總額，輸出人數或明確金額，或表明需要追問。
- `src/application/record-recovery.ts`：回收登記。
- `src/application/abandon-advance.ts`：放棄回收。
- `src/application/list-advances.ts`：未回收查詢。
- `src/telegram/handlers/advances.ts`：`/advances` 與相關 callback。

`LedgerRepository` 新增 `listOutstandingAdvances(ownerId)` 與 `getAdvanceAllocation(ownerId, allocationId)`。前者回傳每筆代墊的原金額、已回收合計、餘額與交易對象，由 SQL 聚合完成。

領域與應用層不得引用 grammy 型別，沿用既有分層。

## 10. 測試策略

- **純函式**：餘額計算；先進先出分配（剛好用盡、不足、超額）；放棄回收的兩種拆分；分帳解析矩陣（`一半`、`三個人平分`、除不盡、明確金額、無分帳語句）。
- **領域**：三種新帳務形狀通過驗證；回收超過代墊金額被拒；`recovers_allocation_id` 出現在非回收配置被拒；代墊缺交易對象被拒。
- **Repository**：`listOutstandingAdvances` 的聚合正確；放棄回收後餘額歸零；migration 0005 保留既有資料且外鍵完整。
- **應用層**：一次回收多筆；超額回收產生額外配置並要求分類；部分放棄與全額放棄；回收後再放棄剩餘。
- **Telegram**：AC-11 至 AC-14 的完整流程；未知對象的建立確認；`/advances` 分組、收款與放棄。
- **統計**：固定資料下，代墊計入實際流出但不計入個人消費；回收計入實際流入但不計入個人收入；分類排名不含代墊。
- **回歸語料**：`tests/fixtures/parser-corpus.ts` 補入代墊語句，確認 M3a 的切分規則不會把分帳語句切開。

## 11. 驗收對應

| 案例 | 語句／操作 | 預期 |
|---|---|---|
| AC-11 | `聚餐 1260，我先付，朋友欠一半` | 交易總額 1,260；個人支出 630、代墊 630，代墊帶交易對象 |
| AC-12 | 回收代墊 300 | 建立流入與回收配置，該筆代墊未回收餘額為 330 |
| AC-13 | 放棄回收剩餘 330 | 原配置拆為代墊 300 與支出 330，原月份個人消費增加，稽核事件含前後快照 |
| AC-14 | 代墊 630、收到 700 | 630 沖抵代墊，70 自成配置並要求另外分類 |

AC-11 的「聚餐」在現有參照資料中沒有對應分類，依「未知參照不猜測」原則會先追問分類，補齊後再完成草稿。這與 M3a 驗收時的處理一致，屬於預期行為。

## 12. 風險與取捨

- **追溯修改歷史**：放棄回收會改變已結束月份的統計數字。這是規格明定的行為，稽核事件保存前後快照可供追溯，但任何已匯出的舊報表會與系統不一致。M5 的 Sheet 鏡像需要處理重新同步，屆時一併考慮。
- **先進先出分配**：系統一律以最早的代墊先抵，M3b 不提供逐筆指定。這是可預測的規則，但不一定符合對方的本意；預覽會逐筆列出沖抵結果，不符時使用者取消即可，代價是該次還款必須改以其他方式記錄。是否需要逐筆指定，留待 M6 dogfood 判斷。
- **交易對象重複**：當場建立降低了記帳阻力，但錯字會產生重複對象（「小明」與「小 明」）。名稱以 Unicode 正規化後不分大小寫比對，可擋住部分情形；合併重複對象的維護功能留待後續里程碑。
- **分帳語句誤判**：`三個人平分` 需同時解析人數與名字。名字數量不符時一律追問，不猜測誰是誰。
