# M2 帳務核心設計

- 日期：2026-09-18
- 狀態：已核准，可進入實作規劃
- 里程碑：M2－帳務核心完整化

## 1. 目的

M2 將 M1 的單一支出切片擴充為一致的 TWD 帳務核心。系統將支援收入、一般支出、信用卡支出、內部轉帳、信用卡繳款、退款、轉帳手續費、受控參照資料、正式帳本異動及精確摘要。

本設計涵蓋路線圖驗收案例 AC-01 至 AC-08、AC-15、AC-16、AC-18 及 AC-19。設計必須保留 M1 資料，並讓 Telegram、SQLite 與解析器維持在領域規則之外。

## 2. 範圍

M2 包含：

- 完整驗證本階段支援的 `funds_effect` 與 `purpose` 組合；
- 帳戶、兩層分類、商家、交易對象及自由交易標籤；
- 收入、支出、信用卡支出、內部轉帳、信用卡繳款、退款及手續費流程；
- 已確認交易的修改與軟刪除；
- 不可變稽核事件及來源事件追溯；
- 使用精確十進位計算今日、本月及分類摘要；
- 僅針對 M2 驗收語句的確定性解析；
- 從 M1 schema 無資料遺失地遷移至 M2。

M2 不包含多筆輸入、對話式欄位追問、代墊與回收、借貸、持久化工作、Google Sheets、自動備份、AI、自然語言查詢、外幣及分期付款計畫。這些能力維持在後續路線圖里程碑。

## 3. 聚合邊界

`Transaction` 是聚合根。其金額配置、標籤及由該交易發出的交易關聯必須與交易一起原子異動。參照實體以 ID 選取，不由交易聚合擁有。

一筆已確認交易包含：

- 識別：`transactionId`、`ownerId`、`requestId`、`sourceEventId`；
- 來源：`sourceType`、`sourceRef` 及受長度限制的原始輸入快照；
- 發生時間：`occurredDate` 及可選的 `occurredTime`；
- 金額：正數 TWD `Money`；
- 參照：可選的 `accountFromId`、`accountToId`、`merchantId`、`counterpartyId`；
- 內容：金額配置、自由交易標籤 ID 及可選備註；
- 生命週期：`confirmed` 或 `deleted`、時間戳及可選的 `deletedAt`。

每筆金額配置包含：

- `allocationId`、正數 TWD 金額、`fundsEffect` 及 `purpose`；
- 一個啟用中的葉節點分類 ID；
- 可選的交易對象 ID 及備註。

系統語意必須保存在受控欄位。退款、轉帳、手續費、代墊及借貸是財務用途，不是分類或自由標籤。

## 4. 不變條件

領域層必須在持久化之前驗證以下規則：

1. 交易與金額配置使用有限、正數的 TWD 十進位字串。
2. 所有金額配置精確加總為交易總額。
3. 每筆金額配置使用本階段支援的資金效果與財務用途組合。
4. 分類必須是同一擁有者所擁有、啟用中的葉節點分類。
5. 帳戶、商家、交易對象及標籤必須屬於同一擁有者。
6. 內部轉帳必須具有不同的 `accountFromId` 與 `accountToId`。
7. 一般收入及退款若指定帳戶，必須使用收款帳戶。
8. 一般流出及信用卡繳款若指定帳戶，必須使用付款帳戶。
9. 信用卡消費以該卡作為 `accountFromId`，且不得有收款帳戶。
10. 退款關聯必須由退款交易指向同一擁有者之有效、已確認支出交易。
11. 已刪除交易不得修改、重複刪除或作為新的退款目標。
12. 每次異動及其 AuditEvent 必須在同一個 SQLite transaction 中提交。

## 5. 支援的帳務形狀

| 流程 | 資金效果 | 財務用途 | 帳戶形狀 | 統計影響 |
|---|---|---|---|---|
| 現金或銀行收入 | `inflow` | `income` | 可選 `accountToId` | 資金流入及個人收入 |
| 現金或銀行支出 | `outflow` | `expense` | 可選 `accountFromId` | 資金流出及個人支出 |
| 信用卡支出 | `none` | `expense` | 信用卡置於 `accountFromId` | 僅個人支出 |
| 銀行間轉帳 | `internal` | `transfer` | 兩個帳戶皆必填 | 不影響淨資金流及個人收支 |
| 提領現金 | `internal` | `transfer` | 銀行轉現金 | 不影響淨資金流及個人收支 |
| 信用卡繳款 | `outflow` | `transfer` | 銀行轉信用卡 | 僅資金流出 |
| 現金或銀行退款 | `inflow` | `refund` | 可選 `accountToId` | 資金流入並減少個人支出 |
| 信用卡退款 | `none` | `refund` | 信用卡置於 `accountToId` | 僅減少個人支出 |
| 轉帳手續費 | `outflow` | `fee` | 與轉帳相同的付款帳戶 | 資金流出及個人支出 |

含手續費的轉帳是一筆交易。交易總額是付款帳戶實際減少的金額，包含一筆本金轉帳配置及一筆手續費配置。AC-19 的交易總額為 1,015，配置分別為轉帳 1,000 與手續費 15。

## 6. 參照資料

### 6.1 帳戶

帳戶類型為 `cash`、`bank`、`credit_card` 及 `e_wallet`。帳戶具有穩定 ID、擁有者、顯示名稱、類型、幣別、啟用狀態及時間戳。M2 不計算帳戶餘額。

### 6.2 分類

分類固定為兩層：根分類及可選的子分類。金額配置必須參照葉節點。每個分類具有 `income` 或 `expense` 類型；手續費及退款配置使用支出分類。停用分類會阻止未來選取，但不使歷史資料失效。

應用程式啟動時，migration 會針對設定的擁有者，以應用程式定義的穩定 key 及冪等寫入方式建立規格中的初始收入與支出分類。

### 6.3 商家與交易對象

商家識別企業或收款方。交易對象識別關係型財務流程中的個人或組織。M2 保存標準紀錄，但別名與分類規則延後實作。

### 6.4 標籤

M2 標籤是擁有者自訂、交易層級的標籤。標籤名稱經 Unicode 正規化後，以不區分大小寫方式在同一擁有者內保持唯一。金額配置層級的系統標籤從 M3 代墊模型開始實作。

## 7. 交易關聯與退款

M2 支援一種關聯類型：`refund_of`。關聯由退款交易指向原始支出交易。

退款不得修改原交易。已關聯退款沿用原始配置分類，除非使用者明確確認另一個支出分類。未關聯退款只有在明確指定支出分類時才允許入帳。退款統計歸屬退款發生日期，且可使淨支出為負數。

多筆部分退款可指向同一筆交易。M2 不禁止退款總額超過原交易，因為手續費、合併退款及不完整歷史匯入會讓嚴格限制產生誤判；確認前的預覽必須揭露退款金額及目標。

## 8. 生命週期與稽核

建立、修改、軟刪除、建立關聯及解除關聯正式資料時，都必須產生 AuditEvent。每個異動命令攜帶新的 `sourceEventId`；Telegram 編輯及 callback 必須記錄為不可變輸入事件，不得覆蓋較早事件。

M2 稽核動作為：

- `transaction_created`；
- `transaction_updated`；
- `transaction_deleted`；
- `transaction_linked`；
- `transaction_unlinked`。

只有建立操作的 `beforeJson` 可為空；只有刻意移除關係的操作可讓 `afterJson` 為空。軟刪除必須保存前後兩份快照。快照包含完整領域表示，但不得複製秘密或執行期設定。

修改操作會原子取代聚合中可編輯的欄位與金額配置，同時保留 `transactionId`、`ownerId`、`requestId`、原始建立時間及來源鏈。軟刪除只設定狀態及 `deletedAt`，不得實體移除交易、配置、關聯或稽核資料。

## 9. 持久化演進

Migration `0002_accounting_core.sql` 新增參照、關聯、標籤及稽核資料表；若 SQLite 約束需要，則重建 M1 的交易與金額配置資料表。

Migration 必須保證：

- `0001_initial.sql` 保持不變；
- 現有 M1 交易保留 ID、request ID、來源事件、金額、配置及確認時間；
- 現有自由文字分類依正規化名稱映射至預設分類 ID；
- M1 的 `food / meal` 值映射至標準的餐飲／午餐分類；
- migration 以原子方式執行，且只在資料複製與完整性檢查成功後記錄 schema version 2；
- foreign key 保持啟用，且 `PRAGMA foreign_key_check` 不得回傳資料；
- version 2 記錄完成後，重複呼叫 migration 不得再改變資料。

M2 草稿仍以 draft JSON 作為真相來源，但改用擴充後的領域 schema。M2 不支援確認 migration 前尚未完成的 M1 草稿；migration 會將它們標記為 archived，並保留 JSON 與來源事件以供追溯。

## 10. 查詢模型與統計

`LedgerSummary` 接受擁有者 ID 及包含起訖日的本地日期範圍。只有未刪除且已確認的交易納入計算。

回傳值全部使用精確 TWD Money：

- 實際流入：`fundsEffect=inflow` 的總和；
- 實際流出：`fundsEffect=outflow` 的總和；
- 淨資金流：實際流入減實際流出；
- 個人收入：`purpose=income` 的總和；
- 個人總支出：`purpose in (expense, fee)` 的總和；
- 退款：`purpose=refund` 的總和；
- 個人淨支出：個人總支出減退款；
- 個人收支結餘：個人收入減個人淨支出；
- 分類合計：各分類的支出與手續費減去退款。

`internal` 與 `none` 不影響實際流入或流出。`transfer` 不影響收入或個人支出。已刪除交易排除於所有一般讀取與摘要。

`/today` 以 Asia/Taipei 的今日日期同時作為起訖日。`/month` 以本月第一日至今日為範圍，回傳同一組雙口徑指標及分類排名；分類先依淨支出遞減，再依穩定分類名稱排序。

## 11. 確定性輸入邊界

M2 僅將規則解析器擴充至足以支援下列驗收形式：

- 一般支出，包含既有午餐案例；
- 以正號金額表示的薪資收入；
- 同時包含相對日期、商家及已知帳戶的支出；
- 指定來源與目的帳戶的轉帳；
- 信用卡消費與繳款；
- 已明確選取或由系統推薦原交易的退款；
- 明確列出本金及手續費的轉帳。

帳戶、分類、商家、日期、金額或退款目標未知或互相衝突時，解析器回傳結構化的缺少／歧義結果。解析器不得自行建立參照資料，也不得在同等候選間猜測。對話式追問狀態仍屬 M3 範圍。

## 12. 應用與轉接器邊界

領域函式負責驗證聚合及計算摘要，不得匯入 grammY 或 SQLite。應用服務協調 repository 與 transaction 邊界。SQLite adapter 負責解析參照及保存正規化資料列。Telegram handler 將指令與 callback 轉換為應用命令。

M2 新增以下應用操作：

- 建立及確認各種支援的交易形狀；
- 修改及軟刪除已確認交易；
- 選取並關聯退款目標；
- 列出最近的有效交易；
- 計算今日、本月及分類摘要。

每個寫入操作都必須限制於擁有者範圍，並在適用時依 request 或來源事件保持冪等。

## 13. 錯誤處理

領域驗證回傳可供預覽或 Telegram 回覆使用的明確問題路徑。應用服務必須區分找不到資料、擁有權不符、無效生命週期轉換、過期異動、重複 request 及參照已停用等錯誤。

SQLite 操作必須是原子的。稽核寫入、關聯寫入、配置取代或影響摘要的更新若失敗，整個異動都必須回滾。Telegram 錯誤不得揭露 token、完整財務原文、擁有者 ID 或 SQL 細節。

## 14. 測試與驗收

測試分層如下：

- 領域表格測試涵蓋每一種支援及拒絕的資金效果／財務用途形狀；
- migration 測試升級含資料的 M1 database，並驗證 ID、來源關聯、分類映射、foreign key 及冪等性；
- repository 測試涵蓋原子修改、軟刪除、退款關聯、稽核快照、擁有權及重複 request；
- 摘要 fixture 使用精確 Decimal 證明每個指標及分類合計，包含負數淨支出；
- parser 測試只涵蓋已指定的確定性形式及參照歧義失敗；
- Telegram 測試涵蓋預覽、callback、`/today`、`/month`、異動授權及資料最小化；
- smoke 與 Docker 測試驗證既有資料的 migration 與啟動流程。

M2 完成條件為 AC-01 至 AC-08、AC-15、AC-16、AC-18 及 AC-19 全數通過、固定摘要 fixture 的每個數值完全精確、M1 資料無損升級，且 Telegram 人工驗收已有紀錄。
